ver

A new spring for version control.

from the Latin ver, “spring”

Alpha release
$ cargo install ver-vcs

Why ver?

Content-defined chunking

Files are split using FastCDC, so only changed chunks are stored. Deduplication is built in.

BLAKE3 hashing

Every chunk is content-addressed with BLAKE3 for integrity and fast lookups.

Cloud sync

Push and pull snapshots to S3, GCS, or Azure Blob Storage with incremental uploads.

Simple CLI

Snap to save, goto to restore. No staging area or branch management.

Merges

Merge between repositories with interactive conflict resolution.

Encrypted secrets

Store cloud credentials encrypted with age (x25519) right in your repo.

Quick start

# Initialize a repository
ver init

# Create some files and take a snapshot
echo "hello" > hello.txt
ver snap my-first-snapshot

# Make changes and snapshot again
echo "world" >> hello.txt
ver snap my-second-snapshot

# View history
ver log

# Go back to the first snapshot
ver goto my-first-snapshot

# Diff a file between snapshots
ver diff hello.txt -a my-second-snapshot

How it works

When you run ver snap, each file is split into content-defined chunks using FastCDC. Each chunk is hashed with BLAKE3, compressed with zstd, and stored in .ver/blobs/. Snapshots, which map file paths to their chunk lists, are stored in an embedded redb database.

Syncing walks the snapshot graph to find chunks the remote is missing, uploads them in parallel, then writes the head pointer. Cloning downloads all chunks and reconstructs your files from the snapshot graph. Because chunks are content-addressed, identical data is never stored or transferred twice.

Roadmap

Coarse plans for future development, expected through the end of 2026 and into 2027.

  • Unified I/O interface that encompasses FS and object storage, allowing operations like cp and merge across storage backends
  • Single-node server to manage syncs and clones
  • UI attached to the server to display, navigate, and share ver repositories
  • Multi-node server
